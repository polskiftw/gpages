# Math-first development contract

## Architectural decision

The **procedural maze math is the product**, not the SDL3/OpenGL demo.
The 3D renderer is a replaceable consumer of an already validated
logical + geometric maze. No renderer is permitted to silently choose
a wall, invent a staircase connection, or change graph reachability.

A top-down floor preview must show the **actual generator's output**,
not a separate JS/Python approximation. The current maze-preview tool
calls the same Maze::passages API as all other code.

## What is proved TODAY (topology v1)

- The world is a finite rectangular lattice of tile cells.
- Every cell is reachable through a connected graph of openings.
- Horizontal cell carving in a 32 x 32 chunk is randomized DFS;
  chunk-to-chunk mandatory connections arise from a hierarchical
  tree independent of chunk visitation order.
- Changing the seed changes the maze. Changing loop_bps adds
  horizontal openings on top of the base tree. stair_bps adds
  *abstract* same-XY vertical graph edges between floor levels.
- The separate long-stair network adds abstract stair interior
  nodes with optional floor entrances. It does not reserve
  collision-free run length or 3D volume in the ordinary maze.

These guarantees do NOT yet imply a playable 3D building.
We will not describe abstract up/down links as physical stairs
until their required geometry is reserved and collision-validated.

## The preview phase

The first math-facing deliverable is an **offline HTML + SVG gallery**
generated by the existing C++ maze library. It allows comparison of:

- The perfect winding DFS maze (zero optional loops)
- Exactly the same seed with default 6% optional extra openings
- Exactly the same seed with 25% optional extra openings
- A different seed under default settings
- A multistory example with U/D/B markers and floor selection

Each wall is drawn directly from the exact N/E/S/W passage bitmask.
Stats measure dead ends, turns, straights, T junctions, crosses and
abstract vertical edges per floor. The C++ regression tests assert
the drawn number of wall segments agrees with the real graph's edges.
Preview width/height are capped for readability; actual world
dimensions are unaffected by this visualization limit.

The static index.html and single-file standalone.html operate offline without a service, browser
plugin, JavaScript maze reimplementation, build daemon or GPU. This
means the gallery cannot create arbitrary new seeds without rerunning
the C++ generator. The CLI supports arbitrary seeds and floors.

## Architecture to settle BEFORE world-scale 3D rendering

1. **Topology:** a deterministic graph of permitted transitions
   over tiles, floors, rooms and staircase interiors. This retains
   mandatory global connectivity by construction.
2. **Architectural layout:** derive a definitive wall/floor/ceiling
   layout, one-tile-wide or wider corridor sections, optional
   compact mult-tile rooms, and valid doors. No mandatory corridor
   edge may disappear as a consequence of adding a room or stairs.
3. **Physical stair planning:** allocate a deterministic multi-tile
   footprint and volume BEFORE ordinary corridor carving. A
   long stair may cross many floor layers and change its solid/hollow
   undercarriage construction at whole-story landings. Presence
   of side walls and availability of intermediate-floor exits
   are independent decisions.
4. **Overlapping XY, distinct elevation:** represent a ground-level
   corridor beneath a raised staircase and the stair treads above
   as separate spatial/graph layers. Shared XY position DOES NOT
   create a connection; only deliberate landings/doors do.
5. **Geometric validation:** check player-relative headroom, width,
   step height, all solid volume intersections, ceiling cutouts,
   stair continuity, one-way traps and the reachability of every
   mandatory connection. These dimensions are ratios, not meters.
6. **Streaming invariant:** every layout feature, reservation,
   room, stair ID and door must be reproducible from world seed,
   coordinates, algorithm version and settings. Separate chunk
   requests (and differing cache sizes) must produce matching seams.
7. **Renderer:** consume this completed and verified layered
   geometry as meshes/colliders. The renderer must not make
   generation decisions on its own.

The choice of how to reserve multi-cell stairs without invalidating
the current single-cell Up/Down macro-portal design is **UNSOLVED**.
The existing topology connectivity proof must be retained or
replaced with an equally rigorous geometry-aware one.

## Design parameters to compare visually

These must remain separately adjustable; do not quietly conflate
them or freeze their values before we examine example maps:

- World dimensions (horizontal tile count and vertical floor count)
- Seed / generation algorithm version
- Corridor turn bias and distribution of straight-run lengths
- Optional loop/shortcut density
- One-tile default corridor width versus deliberate wider corridors
- Room frequency, footprint distribution, and entrances per room
- Vertical stair frequency, height spans, entrance selection,
  stair type, open/solid undersides, enclosure styles
- Underpass frequency (only where physically possible)

**Existing implemented knobs:** world dimensions, seed, loop_bps and
stair_bps. Most room and corridor shape controls are proposals,
not code yet. Changing an existing seeded algorithm requires an
explicit new generation version; old previews/saves must not
silently change because a renderer was upgraded.

## No giant empty fields

A 10000 x 10000 maze does not imply a 10000 x 10000 open space.
The current generator consists of connected single-cell corridors;
it contains no intentional multi-cell chambers or open-plan areas.
We will preserve a claustrophobic corridor-first option. Any room
or broad passage is an explicit parameterized architectural feature
with bounded footprints, not a side effect of scaling world dimensions.

## Acceptance criteria for the mature generator

- Given fixed version/seed/settings, repeated generation is bit-identical
  irrespective of chunk request and eviction order.
- Exact floor-plan SVG/HTML previews and the rendered world derive from
  one authoritative set of topology/geometry decisions.
- Every intended pair of neighboring traversable areas has a valid
  physical passage, without clipping or discontinuous staircase runs.
- Shared horizontal location does not cause unintended underpass/stair
  connections; solid undercarriages truly prevent passage.
- Finite-world reachability can be independently validated for bounded
  test worlds; huge worlds preserve their proof by construction rather
  than requiring a full-world traversal in RAM.
- No renderer, 3D art, textures or collision approximations are used to
  "fix" geometry that the generator should have laid out correctly.
